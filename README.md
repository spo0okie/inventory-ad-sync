# AD-Inventory-sync
Скрипт двусторонней синхронизации AD с БД инвентаризации

Для увольнения сотрудников вызывается скрипт из скриптов управления https://github.com/spo0okie/ad-usermanagement

## Синхронизирует поля БД -> AD:
* ФИО (Название объекта АД, Выводимое имя, Имя, Фамилия)
* Табельный номер и ИД организации
* Организация
* Подразделение
* Должность
* Мобильный, внутренний, городской номер телефона
* E-Mail (если не в корп. домене: напр. кадры прописали личную почту)
* UID

## Синхронизирует поля БД <- AD:
* Login
* E-Mail (если в корп. домене: мы выдали корп. ящик)

## Привязка компьютеров к сервисам (comps-to-services.ps1)
Отдельный маленький скрипт в этом же репозитории: раскладывает компьютеры из указанных OU
по сервисам в инвентаризации. Нужен для динамически создаваемых машин (VDI) - объект AD
появляется в своем OU, а в инвентаризации ОС надо прицепить к соответствующему сервису.

Работает **только на добавление**: чужие связи (проставленные руками или другим OU) не трогаются,
машины, пропавшие из OU, от сервиса не отцепляются.

```
comps-to-services.cmd
powershell.exe -noprofile -executionpolicy bypass -file comps-to-services.ps1 vdi-0123
```

ОС ищется по `DNSHostName` (если он пуст - по короткому имени), архивные записи пропускаются.
Запись в инвентаризацию идет через тот же `$write_inventory`, что и основной скрипт,
логи - в тот же `$logfile`.

## С какой кадровой записью синхронизируется учетка

В инвентаризации одному человеку соответствует не одна запись, а по одной на каждое трудоустройство:
основное место работы, совместительство в другой организации и т.д. Учетка AD в каждый момент связана
ровно с одной из них — с той, чьи организация, подразделение и должность выгружаются в AD.
Связь пересматривается **на каждом прогоне**.

### 1. Находим человека

Пользователь ищется в БД последовательно, до первого совпадения: по логину, по табельному номеру,
по UID (ИНН/СНИЛС), по ФИО и, наконец, по ФИО как по табельному номеру. Найденная запись нужна
только чтобы понять, что это за человек — дальше по его UID (а если UID не заполнен, то по ФИО)
поднимаются **все** его кадровые записи.

Последний вариант — рабочий приём при заведении сотрудника: в имя новой учетки вписывают табельный
номер, и первая же синхронизация подставляет настоящее ФИО. При поиске по имени вначале используется
`displayName` (если нет — `cn`), а если ни один вариант не дал результата — пробуем `name` объектов,
отличающийся от предыдущих вариантов.

### 2. Отсеиваем те, на которые переключаться нельзя

* **занятые другой учеткой AD** — если в записи стоит чужой непустой логин, она не наша: у человека
  может быть несколько учеток (например по одной на организацию), и каждая держится своего
  трудоустройства;
* **в неаффилированной организации** — перевести учетку в другую организацию можно только внутри
  группы `$affiliatedOrgs`; организация, не входящая ни в одну группу, замкнута сама на себя;
* **уволенные** — целью переключения может быть только действующее трудоустройство.

Текущая привязка из списка не выбывает никогда: если переключиться некуда, синхронизируемся с ней —
и увольняем учетку, когда это трудоустройство закрыто.

### 3. Из оставшихся выбираем лучшую

Записи сравниваются по признакам, каждый следующий учитывается только при равенстве предыдущих:

1. **действующая** — уволенная проигрывает всегда;
2. **в приоритетной организации** (`$stickyOrg`);
3. **уволенная позже** — работает только при первом связывании, когда действующих записей нет вовсе;
4. **лучший тип трудоустройства** — `Persg` из кадровой системы, меньше значит лучше;
5. **текущая привязка** — если в рейтинге несколько равнозначных по предыдущим признакам записей приоритет - остаться на текущей;
6. **более новая запись** — если текущей связи еще нет, и нужно выбрать из нескольких равнозначных - выбираем самую свежую.

### Зачем это нужно

Сотрудника переводят с должности на должность: в пятницу уволили, в понедельник приняли. Прогон в
выходные видит из действующего только совместительство в другой организации и переключает учетку на
него; понедельничный прогон возвращает ее в приоритетную организацию, на новое основное
трудоустройство. Вместе с учеткой переезжает и все нажитое на прежней кадровой записи — внутренний
номер телефона, техника, ПК, лицензии, доступы, журнал входов (метод `users/migrate` инвентаризации).

Что именно отсеялось и почему учетка переключилась, видно в логе при `$global:DEBUG_MODE=1`.

Инклудит файл ..\config.priv.ps1 следующего содержания
```powershell
#домен организации
$domain="domain.local"

#организация, имеющая приоритет над прочими при множественном трудоустройстве
#задается ID организации или ее именем; $false - приоритета нет
$stickyOrg=1

#группы аффилированных организаций: учетку разрешено переводить с одного трудоустройства
#на другое только внутри группы. Организация, не входящая ни в одну группу, сама по себе -
#учетка ходит только между ее собственными трудоустройствами.
#организации задаются ID или именами, групп может быть несколько
$affiliatedOrgs=@(
	@(1,2,3)
)

#пары подразделений для синхронизации: где брать пользователей (u_OUDN)
#и куда переносить уволенных (f_OUDN). Обрабатываются все пары по очереди
#stickyOrg можно переопределить для каждого OU отдельно
$inventory2ad_sync=@(
	@{
		u_OUDN="OU=Пользователи,DC=domain,DC=local";
		f_OUDN="OU=Уволенные,DC=domain,DC=local";
		#stickyOrg=2;
	}
)

#писать ли изменения в АД?
$write_ad=$false
#разрешить автоматическое увольнение при синхронизации
$auto_dismiss=$false
#внешний скрипт увольнения, если указан, то будет вызван с логином отключаемой учетки в качестве аргумента
$dismiss_script=$false
#исключить автоматическое уольнение этих логинов:
$auto_dismiss_exclude=@(
	'pupkin.v',
	'lohankin.v', 
	'lenin.v'
)

#почтовые домены Exchange: для адресов в этих доменах источником считается АД,
#и почта синхронизируется в обратную сторону (АД -> БД инвентаризации)
$exchange_domains=@(
	'domain.local'
)

#URL сервиса запросов в таблицу пользователей САП
$inventory_RESTapi_URL="http://inventory.domain.local/web/api"
#учетка для Basic-авторизации в REST API
$inventory_user_login="inventory_ad_sync"
$inventory_user_password="password"
#поддержка нескольких организаций
$multiorg_support=$false
#формат даты (приема, увольнения, др) в САП
$inventory_dateformat='yyyy-MM-dd'
#писать ли изменения в БД инвентаризации
$write_inventory=$false

#путь к библиотекам (spo0okie/ps1.libs); можно не задавать -
#тогда используется $PSScriptRoot\..\libs.ps1 рядом со скриптом
$libs_path="C:\Joker\Works\PS\libs.ps1"

#OU с компьютерами и сервисы, в которые их надо добавлять (для comps-to-services.ps1)
#service задается ID сервиса или его именем, можно списком - тогда машина попадет во все
$comps2services_sync=@(
	@{
		OUDN="OU=VDI,OU=Comps,DC=domain,DC=local";
		service="VDI: Бухгалтерия";
	},
	@{
		OUDN="OU=VDI-Dev,OU=Comps,DC=domain,DC=local";
		service=@(42,"VDI: Разработка");
	}
)

#логфайл синхронизации
$logfile="C:\Joker\Works\PS\user_management\SAPsync\log\user_sync.log"
```


## История изменений
v5.3 + Поиск по ФИО теперь пробегает `displayName`, затем `cn` (если он отличается от `displayName`), и
      + в крайнем случае — `name`, чтобы не пропустить объект, который отличается от отображаемого имени  
v5.2 + Приоритетная организация ($stickyOrg) при множественном трудоустройстве  
      + Все трудоустройства пересматриваются на каждом прогоне, а не только когда текущее уволено  
      + Трудоустройства, занятые другой учеткой АД, в выборе не участвуют
        (у человека может быть несколько логинов - каждый держится своего)  
      + Группы аффилированных организаций ($affiliatedOrgs): за пределы группы
        (а вне групп - за пределы организации) учетку не переводим  
      + Уволенные трудоустройства исключены из пула переключения: приоритетной
        может быть только действующая запись  
      + При равенстве трудоустройств по существу сохраняется текущая привязка,
        чтобы не плодить переключения между равнозначными записями
